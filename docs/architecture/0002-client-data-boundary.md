# ADR 0002: Клиентская граница данных

## Статус

Принято

## Контекст

Продуктовым страницам нужны асинхронные данные, фильтрация, состояния загрузки и отмена устаревших запросов. Настоящий backend пока не входит в границу frontend-стенда, однако страницы не должны импортировать тестовые данные напрямую.

## Решение

Все чтение продуктовых данных проходит через `src/api/relayDeskApi.ts`. API возвращает `Promise`, принимает `AbortSignal` и скрывает источник данных. Компоненты используют общий `useAsyncData`, который представляет состояния загрузки, успеха и ошибки явным типизированным объединением.

Исходные записи находятся в `src/data/fixtures.ts`. Во время первого запуска API создаёт рабочее состояние, а после мутаций атомарно сохраняет массив заявок в versioned `localStorage`. Все страницы читают тот же store; событие `relaydesk:datachange` обновляет связанные показатели shell. Доменные типы и подписи хранятся отдельно в `src/domain`.

Тестовый контроллер API может детерминированно отклонить следующую операцию. Это позволяет проверять ошибки чтения и записи без случайности и без скрытого изменения данных.

## Последствия

- страницы можно переключить на HTTP-клиент без изменения их продуктовой модели;
- loading/error/empty-состояния проверяются уже сейчас;
- локальная реализация моделирует задержку, отмену и контролируемые отказы, но не HTTP и многопользовательскую синхронизацию;
- `localStorage` сохраняет мутации между перезагрузками одного браузера, но не является защищённым серверным хранилищем;
- при появлении реального API нужно отдельно определить схему валидации ответов и стратегию кеширования.
