# Путеводитель по кодовой базе

Этот документ описывает границы Relay Desk, достаточные для начала самостоятельного исследования. Детали конкретного поведения проверяйте в актуальном коде и тестах.

## Основные каталоги

- `src/pages` — страницы маршрутов и пользовательские сценарии.
- `src/components` — общий каркас и переиспользуемые компоненты.
- `src/api` — единственная граница чтения и изменения продуктовых данных.
- `src/domain` — типы сущностей, статусов и прав доступа.
- `src/data` — исходные демонстрационные данные.
- `src/hooks` — общие React-хуки, включая асинхронные состояния.
- `src/test` — настройка Vitest и Testing Library.
- `docs/product` — продуктовые роли, сценарии, SLA и ограничения.
- `docs/architecture` — принятые архитектурные решения.

## Маршрутизация

Маршруты объявлены в `src/App.tsx` и отображаются внутри `AppShell`:

- `/dashboard` — операционная сводка;
- `/tickets` и `/tickets/new` — очередь и создание заявки;
- `/tickets/:ticketId` — карточка заявки;
- `/catalog` — каталог услуг;
- `/knowledge` и `/knowledge/:articleId` — база знаний;
- `/team` и `/reports` — управленческие разделы с проверкой роли;
- остальные URL — страница 404.

Фильтры очереди хранятся в URL. Это делает результат воспроизводимым и позволяет переходить к отфильтрованному списку из Dashboard.

## Модель данных

Основная сущность — `Ticket`. Заявка связана с организацией, заявителем, очередью, категорией и необязательным исполнителем. Исполнитель относится к команде и имеет роль. Сообщения различают публичные ответы и внутренние заметки, а activity хранит историю значимых изменений.

Каталог услуги задаёт шаблон новой заявки. Dashboard, очередь, команда, навигационный счётчик и отчёты получают показатели из одного рабочего набора заявок.

Точные типы находятся в `src/domain/types.ts`, исходные записи — в `src/data/fixtures.ts`, продуктовые термины — в `docs/product`.

## API, хранение и состояние

UI не импортирует fixtures напрямую. Все операции проходят через `src/api/relayDeskApi.ts`. API имитирует асинхронную границу, поддерживает `AbortSignal`, контролируемые ошибки в тестах и проверяет доменные ограничения.

Рабочий набор заявок хранится в памяти модуля и после успешных мутаций записывается в versioned `localStorage`. Это локальная модель одной браузерной среды, а не backend и не многопользовательская синхронизация.

Глобальной библиотеки состояния нет. Сервероподобные данные загружаются через `useAsyncData`; локальное состояние форм и режимов остаётся внутри страниц. Событие `relaydesk:datachange` обновляет связанные показатели оболочки после мутаций.

## Тестовая инфраструктура

Vitest запускается в `jsdom`, а Testing Library проверяет поведение через доступные роли и подписи. `src/App.test.tsx` покрывает сквозные компонентные сценарии, `src/api/relayDeskApi.test.ts` — контракты данных, ошибки, права и согласованность показателей.

Основные команды:

```bash
npm run typecheck
npm run lint
npm test
npm run build
```

CI выполняет тот же набор после чистой установки `npm ci`.

## Архитектурные границы

- Не добавляйте новую зависимость без конкретной продуктовой или инженерной причины.
- Не обходите `relayDeskApi` прямым импортом fixtures в UI.
- Сохраняйте фильтры, на которые ведут ссылки, воспроизводимыми через URL.
- Изменения модели должны оставлять Dashboard, очередь, команду и отчёты согласованными.
- Настоящие HTTP, аутентификация и серверное хранение пока находятся вне первой версии.

Причины этих решений зафиксированы в ADR 0001 и ADR 0002.
